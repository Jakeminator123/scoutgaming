# Astrid game backoffice

`https://backoffice.bettalotto.se/bo/#shoes` reads the same SQLite database and engine transactions as the shared game. The separate demo backoffice UI was removed; its old URL redirects to the existing BO. The audit engine lives on `codex/astrid-shared-demo` in Scout Croupier and `codex/deal-aligned-boxes` in the Astrid repository. It does not replace the other branch's Partner API / Eventstudio implementation.

## Shoe evidence

The existing Fisher–Yates shuffle still uses `crypto.getRandomValues` with unbiased rejection sampling. Each accepted and rejected uint32 sample is recorded. Each physical card has a stable serial (1–416) assigned before shuffling, in deck, suit, rank order. These serials travel with the actual server-owned cards. A SHA-256 opening commitment covers version, shoe ID, rules, random samples and a private 256-bit nonce. The commitment is stored before any deal and included in the player's shoe summary; nonce, samples, burn and future order stay private. The backoffice can save the opening commitment separately for later comparison.

Eight decks contain 416 cards. Position 1 is the burn. The cut threshold is 312 **including the burn**. The current hand finishes normally; the next round retires the remaining shoe and creates a new one. There is no mid-hand shuffle and no requirement to deal all 416 cards.

On retirement, in the same SQLite transaction as the game, verification:

1. Replays all recorded rejection samples and Fisher–Yates swaps, with no unused samples.
2. Checks the immutable opening commitment, eight copies of every rank/suit and all 416 unique physical card IDs.
3. Matches each numbered draw, including the burn, against the replayed order.
4. Matches every dealt card against the separately recorded engine action log.
5. Matches every unused card against the remainder and reconciles consumed + unused = 416.

A failed verification is stored as `failed`, never green. Existing pre-audit shoes are `incomplete`; their missing history is never reconstructed or presented as verified. An active shoe is `open` and cannot be downloaded. Hole-card values in action records stay redacted until wallet settlement.

Download a closed shoe's bundle and verify locally:

```sh
node tools/verify-shoe.mjs downloaded-shoe.json PREVIOUSLY_SAVED_OPENING_COMMITMENT
```

Omitting the second argument checks against the opening commitment inside the bundle, not an independently retained anchor. This is reproducible shuffle/accounting evidence, **not independent RNG certification** or proof of entropy quality. A system administrator able to rewrite the entire database and all external anchors is outside this integrity model. The lab still needs to test/certify the RNG implementation. Failed/incomplete verdicts need operator investigation.

## Action tree and Jakob's contract

The tree groups committed events by round: player commands / automatic progression → engine command → numbered draws → presentation plan → wallet settlement. Records include request IDs, table versions, shoe IDs, plan IDs, clip IDs, timestamps, parent event references, stakes, returned amount and net result. Bets/join/ready/leave and shoe lifecycle are in table activity. State polls and idempotent retries add no duplicate player actions; rejected transactions roll back audit writes with the game.

This follows the distinction in [Jakob's S02](https://gitlab.com/scout-gg/croupier/-/blob/jakeminator123/work/docs/animation-events/v5-7-days-mvp/s02-spraket.md): game decision, presentation instruction and actual playback are different evidence. Here `presentation.plan` means **scheduled**, not played or heard. This implementation does not claim Partner-SSE, OpenClaw selection or device playback acknowledgements.

Events are hash-linked and append-only through SQLite triggers. Opening commitments and closed shoes are immutable through the application database. The UI shows the latest 100 shoes, 20 complete rounds per page with older-round pagination, and latest 100 table-level actions. Data is a timestamped snapshot; Refresh fetches current data. No invented historical round reconstruction.

## Access and operations

Use the existing backoffice login and admin/superadmin role. Shoes & Decks, Action Tree and Game Media are sections of that same application. The BO server forwards read-only requests to the game over loopback using `GAME_AUDIT_TOKEN`, configured only in the two service environments. Tokens never reach the browser. A player session grants no BO access; reader/staff roles cannot access this audit. Registered media previews use the same role gate and support byte ranges.

The duplicate demo UI and `BACKOFFICE_PASSWORD` login are removed. `/backoffice` redirects to the existing BO, old `/api/backoffice/*` endpoints return 410, and the private audit endpoint rejects missing/wrong tokens, non-loopback callers and browser Origins. The original site's player HTTP Basic login is unchanged. No additional human account or password is required. All audit API responses are no-store.

SQLite tables `audit_shoes` and `audit_events` are additive migrations. Existing balances, cards and rooms are retained. Back up the live DB before deploying. An audit write failure raises/rolls back the related transaction rather than silently losing the audit trail. Keep the data volume monitored; no audit deletion/retention job is installed.

## Transactions and house result

The existing BO Transactions page reads persisted shared_settlements across all matching dates, players and tables, not a recent audit-event page. Stake and payout values are rounded to integer cents before summing. House result = stakes minus total returns; returns include returned winning/pushed stakes, side awards and insurance. Hold is house result divided by stakes (undefined when there are no stakes). Current open committed stakes and uncommitted prepared bets are separate from settled results and independent of the historical date filter. Demo credits are not gaming revenue. No real-money accounting or operating-cost profit is claimed.

New shared_transactions rows are written in the same SQLite transaction as every shared-player balance change: opening credit, round stake, split/double/insurance stake, payout and demo top-up. Request replay and rollback retain the existing exactly-once behavior. Existing players receive a zero-change opening snapshot on first migration; no missing historic balance movements are reconstructed. The page states this coverage boundary. Clearing an uncommitted bet moves no money; the current game has no refund transaction path. Append-only triggers prevent accidental updates/deletes. Migration never changes existing balances or receipts.

Deployment: backend server/transactions.mjs must accompany server/shared-table.mjs and server/server.mjs; existing BO needs the updated service bridge and transactions.mjs UI/navigation/CSS. Preserve the persistent database and take a SQLite online backup before first deployment. Restarting/reverting application code must not replace the database. Test reports use isolated databases, never production wallets.
