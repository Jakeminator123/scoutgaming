# OpenClaw and Render blueprint

The lab's deployable unit is `open-claw/lab/`. It can remain in Croupier or be
copied to the root of a separate repository later. The blueprint is scaffolding:
creating cloud services, supplying credentials and verifying a real model call
are separate deployment steps. No cloud resource is created by running the local
lab.

## Where the keys belong

| Variable | Purpose | Location |
| --- | --- | --- |
| `OPENCLAWAPI_KEY` | Authenticates the Director to the OpenClaw Gateway | Both Render services; optional local root `.env` when connecting to a local/existing Gateway |
| `OPENCLAW_MODEL_API_KEY` | Authenticates OpenClaw to the chosen model provider | **Private Gateway only** |
| `LAB_API_TOKEN` | Authenticates access to the public lab Director | Render Director; generated by the blueprint |
| `LAB_REMOTE_TOKEN` | Local copy of the Director's `LAB_API_TOKEN` | Local root `.env` |

`OPENCLAWAPI_KEY` is this project's variable name. The Gateway startup wrapper
maps it to OpenClaw's official `OPENCLAW_GATEWAY_TOKEN` variable. This bearer is a
Gateway operator credential; keep it on the servers. A provider API key is a
different credential. If the value you have is a provider-issued model API key,
place it in `OPENCLAW_MODEL_API_KEY` and use an independent secret for
`OPENCLAWAPI_KEY`.

The root `.env` is local configuration and is never uploaded by this blueprint.
On Render, enter secrets in the service Environment settings. The Docker build
excludes `.env` files. There is no fallback to an inherited `OPENAI_API_KEY`.
The shipped model route is an explicit example (`gpt-5.4-mini` through
`https://api.openai.com/v1` with `openai-responses`); change
`OPENCLAW_MODEL_BASE_URL`, `OPENCLAW_MODEL_ID` and `OPENCLAW_MODEL_API` together for
another provider. No model request works until its separate credential is set.

## Connection path

```text
Browser on laptop
  -> local lab server (127.0.0.1:4188)
  -> HTTPS public Render Director (LAB_REMOTE_TOKEN)
  -> private Render OpenClaw Gateway (OPENCLAWAPI_KEY)
  -> configured model provider (OPENCLAW_MODEL_API_KEY)
```

The laptop initiates the connection. Render needs no inbound tunnel to the
laptop. The Director owns catalog validation, trigger evaluation and the final
gate; OpenClaw suggests only an eligible variant. The lab's operator chat uses the independent
`croupier-chat` agent, while decisions use `croupier-director`. Both agents deny
all tools and have separate workspaces. Chat cannot write the catalog, run shell
commands, access the game server or change OpenClaw configuration. The editor's
validated API performs explicit catalog edits.

This operator endpoint is not a player-chat integration. Actual Croupier player
chat still needs a separate authenticated, moderated adapter to the bounded
`context.chat.signal` contract; the current lab sets those signals manually.
The development team's GitLab IDE-agent inbox is an entirely separate system
and must never be routed through this OpenClaw deployment.

OpenClaw's HTTP API is normally disabled. The managed configuration enables only
the Chat Completions route used by this adapter. The Gateway is a **private
service**, with its Control UI, terminal, browser and cron disabled. This dedicated
Gateway is not the operator's general-purpose personal OpenClaw installation.
Its configuration is externally managed (`OPENCLAW_CONFIG_READONLY=1`).

### Dashboard access is not enabled yet

The native OpenClaw dashboard is not the lab editor. This blueprint currently
keeps its Control UI disabled and the Gateway private, so it does not create a
public OpenClaw dashboard URL. The desired operator experience is a single
password/secret field, without adding a separate SSO or MFA flow. Native remote
browser access still normally needs one initial device approval; switching to
password mode does not remove that requirement. See the
[pinned sign-in and pairing guide](https://github.com/openclaw/openclaw/blob/v2026.9.5/docs/web/control-ui/connect-and-pair.md).
An SSH tunnel or a separately reviewed HTTPS entry is a follow-up access choice,
not a change already made by these docs. No auth bypass is configured.

## Render setup

1. Make the lab files available on the intended repository branch. In the Render
   Blueprint creation screen select `open-claw/lab/render.yaml` as the Blueprint
   path. Review the services and cost before creating them: the file declares a
   Starter Director, a Standard private Gateway, and two 1 GB persistent disks,
   all in Frankfurt. Service automatic code deployment is disabled with
   `autoDeployTrigger: off`. Blueprint **Auto Sync is a separate setting** and
   defaults to on: after creation, set Blueprint Settings → Auto Sync → No
   for this initially manual rollout. Otherwise a pushed YAML change can still
   update resources. Use Manual Sync for reviewed infrastructure changes and
   Manual Deploy for a reviewed code-only release.
2. Supply `OPENCLAWAPI_KEY` and `OPENCLAW_MODEL_API_KEY` when prompted. Adjust the
   model route if needed. The Director references the Gateway's shared bearer;
   it never receives the provider credential.
3. Deploy the Gateway and Director. `deploy/start-gateway.mjs` generates the
   dedicated config and runs the pinned OpenClaw CLI's strict validation before
   starting. `OPENCLAW_HOSTPORT` is obtained from Render's private-service
   reference; `deploy/start-director.mjs` constructs the internal URL.
4. Put the Director's public HTTPS URL into local `LAB_REMOTE_URL`, and its
   generated `LAB_API_TOKEN` into local `LAB_REMOTE_TOKEN`. Start the local lab
   normally. Remote mode routes decisions, chat and catalog editing to Render.
   The editor therefore edits the **Render catalog**, persisted under
   `/data/catalog`; it does not silently change the local seed JSON.
5. Verify a decision and a chat message from the lab. A healthy `/healthz` only
   proves that the service responds; it does not prove provider credentials,
   model permissions or a successful OpenClaw decision. Check the lab's trace
   for a real OpenClaw response and its gate result.

The public Director requires `LAB_API_TOKEN` for its `/api/` routes. The normal
browser path is through the local server, which attaches the remote token
server-side. Do not paste the Gateway bearer or provider key into browser code.
The remote token permits lab catalog editing as well as chat/decisions: keep this
initial deployment for the lab's operators, rather than publishing it to players.

Both persistent disks are single-instance. They preserve catalog revisions and
Gateway sessions between deploys, but prevent horizontal scaling and cause brief
downtime during redeploys. Export catalog revisions and use disk snapshots for
recovery. A future shared player runtime needs a separate persistence and
capacity design.

## Optional local Docker deployment

Docker Desktop/Engine with Compose v2 is required. Add the three independent
credentials to the existing root `.env`, using `.env.example` as a field guide.
Then run from the Croupier repository root:

```powershell
docker compose --env-file .env -f open-claw/lab/deploy/compose.yaml up --build
```

This publishes only the Director, bound to `127.0.0.1:4189`; the Gateway has no
host port. The Director requires the configured `LAB_API_TOKEN`. Set local
`LAB_REMOTE_URL=http://127.0.0.1:4189` and `LAB_REMOTE_TOKEN` to the Compose
Director token. Start the normal browser lab on 4188; its server forwards
requests to the containers using that token.

To stop the containers while preserving both named volumes:

```powershell
docker compose --env-file .env -f open-claw/lab/deploy/compose.yaml down
```

Do not add `--volumes` when stopping unless you intend to remove persisted lab
catalog edits and OpenClaw sessions.

## Moving to a standalone repository

Copy the contents of `open-claw/lab/` to the new repository root. In `render.yaml`
remove the `open-claw/lab/` prefix from `dockerfilePath`, `dockerContext` and
`buildFilter.paths` in both service definitions; the Director context becomes
`.` and the Gateway Dockerfile becomes `deploy/Dockerfile.gateway`. Select
`render.yaml` as the Blueprint path. Dockerfile contents and Compose relative
paths require no change. A real source-engine adapter remains owned by Croupier;
the lab's frozen public event contract is the integration boundary.

## Version and verification record

- Gateway image: official `ghcr.io/openclaw/openclaw:2026.9.5`, pinned to OCI index
  `sha256:ea298b62be8955d3ef750e2004a610dd90c3a30e5f9886e5d654d78a0c573218`.
  Its public registry manifest was checked on 2026-09-20 and includes Linux amd64
  and arm64. This version uses `agents.entries` and
  explicit ownership for multiple agents, not the older `agents.list` syntax.
- Director runtime: Node 24 container; the source uses no additional packages.
- Local deployment checks cover JavaScript syntax, secret separation, distinct
  chat/decision workspaces and denied tools. The startup wrapper invokes real
  `openclaw config validate --json` in the image before serving traffic.
- Docker is unavailable on the current Windows workspace, so the image build,
  generated config's actual pinned-runtime validation, persistent-disk
  permissions on Render and live provider call remain deployment checks.
